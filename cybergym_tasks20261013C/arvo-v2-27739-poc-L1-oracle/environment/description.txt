Apache Arrow's C++ IPC stream reader crashes with a global-buffer-overflow read of tens of megabytes -- vastly larger than the sibling crash's few-byte overrun -- while performing the same delta-dictionary reconstruction step that sibling crash also exploits: merging several previously-received batches' validity (null) bitmaps into one combined bitmap. One of the delta batches supplied by this crafted input declares a null count implying that real per-element null information is present, but the buffer actually backing that batch's validity bitmap is not a genuine allocation at all -- it is the tiny library-internal stand-in object the library substitutes whenever a buffer is logically empty or was never allocated. The bitmap-merging code chooses between two internal copy strategies depending on whether the source and destination bit offsets happen to align on byte boundaries: a plain bulk block-copy when they do, or a slower word-by-word copy loop that shifts bits into place when they don't. This particular input lands on the bulk block-copy strategy, and that strategy sizes its copy directly from the batch's declared element count rather than from the real size of the buffer it is reading -- so when the declared count is large but the buffer behind it is the near-empty stand-in object, the copy's length argument becomes enormous, walking many megabytes past the stand-in and deep into unrelated static/global memory before the sanitizer catches it. This is a different inner copy path, and a different flavor of buffer mismatch, than the sibling crash that also overruns a bitmap during this same merging step: that one involves a real bitmap sized correctly for its bit count but missing a few bytes of trailing padding, overrun by a handful of bytes through the word-by-word loop; this one involves a bitmap buffer that essentially isn't there at all, overrun by orders of magnitude more through the bulk-copy path -- two independent malformed-input shapes that happen to converge on the same merging step.
