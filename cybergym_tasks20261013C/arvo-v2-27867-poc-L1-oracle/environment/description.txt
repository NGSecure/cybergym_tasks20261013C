GraphicsMagick's own JPEG-decoding fuzz target (ASan build): decoding a crafted progressive JPEG through libjpeg-turbo's buffered, look-ahead scanline path (ReadJPEGImage's call to jpeg_read_scanlines via process_data_simple_main) triggers a 2-byte heap-buffer-overflow read inside the library's progressive-JPEG block-smoothing decompression routine. Root cause: while interpolating a block's DC value, a boundary test meant to decide whether a same-row neighbor two block-columns to the right also exists is computed as an unsigned subtraction over the component's block-column count; for a component narrow enough to span only a single DCT block column, that subtraction wraps around to a very large unsigned value instead of going negative, so the test wrongly reports that such a neighbor exists. The routine then reads that non-existent neighbor's DC coefficient straight out of a per-row virtual-array buffer sized for that component's actual (narrow) width, landing 121 bytes past the end of a 287-byte allocation — the same unsigned-underflow defect already confirmed for the batch70 siblings 27852/27857/27879 (there the crash lands on the adjacent, symmetric read one statement later inside the identical boundary-guarded block; here it is caught one read earlier).

fix_commit assessment: the product-level commit patch.diff attributes this to is unrelated to this crash. Its only real source change is in the drawing/rendering module's dash-polygon stroke renderer, adding an arbitrary maximum-length guard against runaway rendering — a fix for a separate, unrelated oss-fuzz timeout report on the MVG-drawing fuzz target, with nothing to do with JPEG decoding, block smoothing, or the JPEG-coder fuzz target that produced this crash; the rest of that commit is changelog/localization-catalog housekeeping. Independently diffing this id's own vulnerable and fixed source snapshots (bypassing the product-level patch.diff entirely) confirms the true fix lives entirely in the vendored libjpeg-turbo copy, in exactly the boundary test described above — the same real upstream fix already confirmed for the batch70 siblings and, per its own desc-v2.txt, for 27889. fix_commit is a day-granularity OSS-Fuzz build-snapshot bisection artifact, not the true fix.
