This MATLAB MAT-file (version 5) parser reports a use-of-uninitialized-value fault while decoding the header of a top-level variable entry, right at the point where the reader has just finished checking whether it has actually reached a fresh variable boundary and is about to move on to the very next fixed-size header word for that same variable. Every fixed-size binary word the reader consumes while walking a variable's header and payload goes through one shared low-level byte-read helper, and that helper has a single way of reporting a short read. Normally a short read (fewer bytes transferred than requested) is treated as an outright failure. But as a deliberate exception, the very first word read while probing for the start of a new top-level variable is allowed to fail silently on end-of-file with zero bytes transferred, since running out of stream exactly there is the ordinary, legitimate way a well-formed file ends -- and the calling code correctly guards that specific read by checking both the error flag and the actual transferred-byte count before proceeding. The bug is that this end-of-file leniency was not scoped only to that first, legitimately-optional read; the shared helper applied the exact same "zero bytes transferred equals success" remap unconditionally to every other call site that reuses it, including the very next read immediately afterward -- one that is only ever reached once the code has already committed to "yes, a variable header genuinely starts here" and is therefore not allowed to legitimately hit end-of-file. A crafted stream that is truncated exactly between those two consecutive header words causes that second, mandatory read to come back reporting an all-clear (because zero bytes were transferred and the file position is at EOF), even though the local stack variable meant to receive it was never actually written. The surrounding code's own error check passes cleanly since the helper never raised a failure, so execution falls straight through into using and byte-swapping that never-initialized stack word a few lines later -- exactly the read of uninitialized stack memory the sanitizer traps. The corrective change narrows the end-of-file leniency so it applies only to the small set of reads that are genuinely allowed to land on a legitimate stream boundary (the first probing read of a new top-level variable), while making every other reuse of the same shared helper strict, so a short/EOF read anywhere else -- including immediately after a variable boundary has already been confirmed -- is now correctly reported as a parse error and aborts before any uninitialized value can be touched.
