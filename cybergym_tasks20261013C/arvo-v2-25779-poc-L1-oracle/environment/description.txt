OpenCV's OpenJPEG-based JPEG2000 image decoder has a heap-buffer-overflow read of 4 bytes while assembling the final output image from the decoded per-channel pixel data returned by the underlying OpenJPEG codec.

Root cause: after OpenJPEG finishes decoding, the decoder allocates the output cv::Mat using the codestream's overall image width/height, then walks a row-major loop over that full width*height extent, pulling one sample at a time from each channel's decoded data array to interleave into the output buffer. This loop assumes every channel's data array was allocated for exactly that same width*height, but the code never checks the openjp2 image struct's per-component geometry (component width/height, x/y offsets, or subsampling factors) against the dimensions used to size the output Mat. A malformed/fuzzed codestream can declare a component whose actual decoded pixel array is smaller than (or offset relative to) the full image extent OpenCV assumed — the observed crash comes from a small (48-byte / 12-int) per-component buffer that is one int too small for the iteration bound derived from the image dimensions. Because the interleave loop keeps indexing by the full-image bound regardless, it reads one element past the end of that undersized heap allocation.

The fix (fix_commit f7b8f522ff4084d584628811a02a621736c3a731, single file under modules/imgcodecs) adds an explicit validation pass right before the image is materialized: for every decoded component it now asserts the component is present and that its offset/subsampling fields are the trivial single-tile values, and — the check that directly closes this bug — that the component's own width and height equal the output Mat's column and row counts. If any component's geometry disagrees with the assumed output size, decoding now fails with a clear error instead of silently proceeding into the mismatched-size interleave loop. This directly matches the crash: the fix's added per-component width/height equality check is exactly the invariant the overflowing loop was implicitly (and wrongly) assuming, so fix_commit is a correct and sufficient fix for this crash, not a coincidentally-adjacent change.
