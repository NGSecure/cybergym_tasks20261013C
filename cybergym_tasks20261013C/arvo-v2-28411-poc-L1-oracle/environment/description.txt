LLVM's SelectionDAG instruction-selection fuzz target (llvm-isel-fuzzer, ASan build, x86_64 -O2): while running target-independent DAG combining, folding a sign-extension node triggers an ASan use-after-poison read when the combiner asks for the cached type of one of its operands. That operand is an SDValue produced earlier in the same function's lowering, from building an addition chain for pointer-offset arithmetic, whose owning node lives in a slab carved out of SelectionDAG's node-recycling bump allocator; that allocator explicitly poisons a node's backing storage once the node has been deleted/recycled during the combine pass, so hitting poisoned memory here means the operand SDValue the combiner is still holding refers to a node that had already been torn down earlier in the same combine iteration -- a stale, dangling SDValue reference into freed-and-poisoned SDNode storage, not a fresh out-of-bounds access. The fuzzer's crafted IR drives the combiner into this state deterministically, so the underlying bug is a lifetime/bookkeeping gap in how the combiner tracks which operands remain valid across a single combine step, rather than anything specific to sign-extension arithmetic itself.
