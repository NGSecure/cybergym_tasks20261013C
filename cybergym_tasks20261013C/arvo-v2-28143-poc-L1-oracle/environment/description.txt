uWebSockets HTTP request-line parsing (ASan build, single-shot non-chunked fuzz target): after the parser locates the first header record — the request-line target token — it recomputes that field's stored length by subtracting a small fixed number of trailing bytes that account for the trailing protocol-version text, using unsigned arithmetic. When the target token is shorter than the amount being subtracted, the subtraction wraps around, so the string view is left reporting an astronomically large length while its underlying buffer still only holds a few live bytes. The very next parsing step — a byte-scan across that reported length looking for a query-string delimiter — reads straight off the end of the tiny backing buffer and keeps going past mapped memory, producing a wild out-of-bounds read segfault inside the parser's own header-processing loop, before the request is ever handed off to a user callback. The crashing input is a single minimal raw HTTP-like buffer (not chunked or fragmented) whose target token is only a few bytes long, which is exactly what drives the subtraction negative under unsigned arithmetic.
