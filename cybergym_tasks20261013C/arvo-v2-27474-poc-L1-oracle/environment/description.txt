Apache Arrow's C++ IPC stream reader crashes with an 8-byte out-of-bounds heap read while assembling a dictionary that the crafted input stream sent as a series of incremental "delta" updates rather than as one replacement batch. When the reader has to combine several previously-received delta batches into the final dictionary array, it merges each batch's validity (null) bitmap into one combined bitmap using a word-at-a-time copy routine that always reads a full eight-byte chunk at a time, on the assumption that every source bitmap buffer carries enough trailing slack to make that safe. One of the delta batches supplied by the input carries a validity bitmap buffer sized exactly to its logical bit-length, with no such padding, so the copy routine's last word-sized read walks past the end of that heap allocation by a handful of bytes. The read happens purely inside the low-level bitmap-merging utility itself, after each individual delta batch has already been accepted as a structurally sound array elsewhere in the same dictionary-reconstruction routine -- the gap is specifically that the code which later merges those already-accepted batches together never re-checks that each source buffer is large enough for a padded, word-wise read, only that it is large enough to hold its declared bit count. Reaching this path requires the record-batch stream to first establish a dictionary id via an ordinary (non-delta) dictionary batch and then follow it with at least one delta dictionary batch small enough that its bitmap allocation has no extra room past its exact bit-length.
