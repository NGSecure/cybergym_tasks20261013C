Skia's SkSL shader compiler (skruntimeeffect libFuzzer target, ASan build): compiling a runtime-effect SkSL program in which a function body contains an array-constructor expression (e.g. `float[2](0, 0)`) and that function is inlined at its call site triggers a use-after-poison read. Root cause: the array constructor's synthetic element type is registered only in the callee's own, function-local symbol table at parse time; when the compiler's inliner clones the function body into the caller, the cloned constructor node is given a raw pointer straight to that original type object instead of having its type copied or re-registered into a symbol table that will still be alive afterward. Once inlining finishes and the callee's local scope goes away, the arena region backing that type object is reclaimed/poisoned by the compiler's pool allocator. A later optimizer pass that walks the control-flow graph and inspects the SkSL type category of an expression's operands (as part of algebraic/constant-folding simplification) then dereferences the inlined constructor's now-poisoned type object, and the read of its type-category field is what ASan reports as a use-after-poison.
