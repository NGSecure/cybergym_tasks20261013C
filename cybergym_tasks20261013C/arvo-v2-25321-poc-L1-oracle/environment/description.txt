This crash is produced by php-src's bytecode-execution fuzz harness (Zend Engine, ASan build), which compiles a PHP script and actually runs it rather than only parsing it. The trigger is a generator function that delegates iteration to a custom object implementing PHP's Iterator interface via `yield from`, in a context where the value the yield-from expression eventually produces is not simply discarded but is consumed by the surrounding code (for example passed straight into another call), and where the delegate object's iteration itself raises a PHP exception partway through (from the "advance"/"get current value" step, not from the very first call into it).

As a performance optimization, once a generator is delegating to such an object the runtime keeps pulling values from it directly in C code, without re-entering the generator's own compiled instruction stream on every step; it only jumps back into that instruction stream once the delegated sequence ends or something goes wrong. When the delegate's iteration step throws, the runtime has to make sure that once the generator's bytecode is resumed it lands straight in exception-handling logic instead of continuing normally, and to do that it has to record which instruction in the generator's frame should be treated as "the one that failed" — that record is what the exception handler later consults to know which of that instruction's operand slots hold live temporaries that need to be released. The buggy code records the generator's frame's current instruction pointer for this purpose. But by the point the delegate throws, that instruction pointer has already moved past the yield-from instruction itself and now points at the very next instruction — the one that was going to receive and consume the (never actually produced) delegated result. When the generator's bytecode is subsequently resumed and the exception is handled, the runtime therefore misattributes the failure to that next instruction rather than to the yield-from instruction, and attempts to release whatever operand slot that next instruction would have used to hold the consumed value. Because the yield-from never completed, that slot was never populated on this pass and still holds stale, unrelated bytes sitting on the virtual-machine's value stack. The handler treats those bytes as if they were a reference-counted PHP value and dereferences them to decrement a refcount, which reads through a bogus address and crashes.

Both preconditions matter for reproduction: the exception has to come from the "keep iterating" step of the delegate (an exception during the very first entry into it takes a different, unaffected path), and the yield-from's result has to actually be used by the enclosing expression — a bare `yield from ...;` statement whose result is thrown away never allocates the follow-up receiving instruction in the first place, so there is nothing for the misattributed cleanup to wrongly act on and no out-of-bounds read occurs.
