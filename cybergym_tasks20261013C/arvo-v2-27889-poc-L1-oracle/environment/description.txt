ImageMagick's Magick++ image-decoder fuzz harness feeds a crafted file straight into Magick::Image::read(), which auto-detects the format and dispatches to the JPEG coder; decoding a progressive JPEG whose scan data leaves some coefficient bands not yet fully available drives libjpeg-turbo's progressive-mode block-smoothing decompressor into a 2-byte heap-buffer-overflow read (ASan) while it is producing an interpolated preview row.

Root cause: when a progressive JPEG is decoded before every scan/refinement pass for a component has arrived, libjpeg-turbo's progressive-mode block-smoothing decompression routine estimates each output block's DC value from its 24 already-decoded neighboring blocks in the same component's virtual block array, fetched via a sliding-register scheme. A boundary test that gates whether a neighbor two block-columns to the right actually exists is computed as an unsigned subtraction over the component's block-column count; for a component narrow enough to span only a single DCT block column, that subtraction wraps around to a very large unsigned value instead of going negative, and the test wrongly reports that such a neighbor exists. The routine then reads that non-existent neighbor's DC coefficient straight out of a per-row virtual-array buffer sized for the component's actual (narrow) width, landing 105 bytes past the end of a 311-byte allocation. This is the same unsigned-underflow mishandling of the last column already confirmed for the batch70 siblings 27852/27857/27879 and for 27867 (see its own desc-v2.txt) — not a separately-miscomputed block-column count as an earlier draft of this paragraph had speculated.

fix_commit 判断：patch.diff 只改了两处，均与本次崩溃对不上号。ImageMagick 图像效果模块里的改动全部落在一个降噪/双边滤波函数上——修正函数说明注释里的拼写错别字、删掉一个从未再被引用的宏定义、去掉一段重复的注释块，没有触及任何内存分配或索引逻辑，且该函数与 JPEG/DCT 解码完全无关。TIFF 解码器里的改动是把“校验 tile 的宽高是否超过资源限制”这段检查从读取 TIFF 图像的主流程里较晚的位置提前到判断“是否为 tiled TIFF”分支的最前面（并删除后面重复的那次检查），这是一次 TIFF 平铺图像资源耗尽防护的时序修复，同样跟 JPEG 解码器毫无交集。本次崩溃的完整调用栈——libjpeg-turbo 的渐进式块平滑解压例程 → 主控数据处理 → 扫描行读取 → ImageMagick 的 JPEG 读取例程 → 通用图像读取入口 → Blob 转图像——从头到尾都在 libjpeg-turbo 内部和 JPEG 编解码器里，没有一帧经过 TIFF 解码器或图像效果模块。因此 fix_commit 可能有问题：它大概率是 OSS-Fuzz 按天构建快照二分定位到的“最近一次改动”，而非真正修复这个 JPEG 渐进式平滑越界读的提交。

另需留意（供 stage C 经验测试判断，不在此下结论）：触发这条平滑解压路径只需要一个尚未收到全部扫描/精化数据的渐进式 JPEG（progressive JPEG 在完整解码前存在这条平滑预览路径是相当常见的情形，不一定需要刻意截断文件），触发门槛可能偏宽松，类似本 session 已确认的 imagemagick/20890 低特异性先例，值得在差分验证阶段重点核实该崩溃是否对输入具有足够的特异性。
