One-line: A PHP `Generator` fuzz target that builds a chained `yield from` delegation between multiple generators crashes with a 4-byte heap-use-after-free read inside the Zend engine, triggered while destroying leftover Generator objects during request shutdown.

Root-cause mechanism:
When a script sets up multi-level `yield from` delegation (one generator delegates into a second, which delegates into a third, and so on, possibly with more than one generator delegating into a shared point in the chain), the Zend engine keeps a small per-generator tree structure that tracks which generator in the chain is currently the active "leaf"/"root" of the delegation path, so that resuming, backtracing, or garbage-collecting the chain doesn't have to rescan every generator involved each time.

At request shutdown, the engine's destructor-shutdown loop calls the object destructor for every still-live object. For a `Generator` object this destructor can recurse: because generators in a delegation chain hold references to each other, tearing down one generator in the chain triggers the destructor to also tear down its remaining linked generators via the same routine before it returns. Each time a generator finishes being torn down this way, the routine that maintains the delegation tree's "which generator is current" bookkeeping runs again to figure out which generator is now the effective root/leaf of what remains of the chain.

That bookkeeping routine walks the tree by following stored parent/child/leaf-style pointers between generator objects, and when it settles on the generator object it believes represents the (new) tracked position, it bumps that object's reference count to mark it as still being held by the tree. The bug is that this walk is not guaranteed to be up to date with exactly which generators the *outer, still-recursing* destructor calls have already freed: because the recursive teardown of a branching/chained delegation tree does not fully propagate its pointer updates to every other generator that still references the node being destroyed, a later step of the same shutdown pass can end up following a stale pointer to a generator object an earlier, sibling recursive call in the very same destructor sequence has already released and freed moments before. Incrementing the refcount field of that already-freed object is the 4-byte heap-use-after-free read reported by the sanitizer.

fix_commit assessment:
`fix_commit` dd4a080133b7b0570b629cdfb7c9e2651bdf88f7 is directly on point, not incidental. It replaces the entire generator delegation-tree bookkeeping scheme described above with a differently structured representation (each generator keeps a direct parent pointer plus a cached root/leaf pointer, instead of the old scheme that indexed children by "leaf" identity and lazily patched leaf pointers across the whole chain on structural changes). The rewrite touches precisely the destructor's recursive child-teardown logic, the "which generator is current" tree-walk routine, the child add/remove helpers, and the generator-tree walk used for garbage collection and backtraces — i.e. exactly the call path shown in the crash trace (destructor recursing into itself, which calls into the current-position tree-update routine). The accompanying regression tests specifically construct branching/chained `yield from` trees and then unset one of the generators to force the same destructor-driven, out-of-order teardown scenario the crash exhibits. This is a direct structural fix of the crashing mechanism — unlike the incidental compile-time-macro-config pattern already identified elsewhere in this php-src batch (ids 25601/26504), here the same functions that appear on the crash stack are the ones the patch rewrites, so the causal link is direct rather than indirect.
