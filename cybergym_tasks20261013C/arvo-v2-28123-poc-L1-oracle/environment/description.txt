GraphicsMagick's JPEG coder (MSan build) decodes a progressive JPEG through libjpeg-turbo with the decoder's block-smoothing feature enabled: while several non-interleaved DC/AC scans are being processed, the smoothing logic latches, per color component, how many bits of each coefficient have been resolved so far in both the current scan and the previous scan, so that later, when producing an output row the newest input scan hasn't caught up to, the block-smoothing routine can fall back to blending from the values recorded for the earlier scan instead. The latch buffer holding those bit-count arrays is a single freshly heap-allocated block that libjpeg-turbo's small-object pool allocator never zero-fills. For this crafted input the MSan trace shows the previous-scan half's per-component AC-coefficient slot genuinely gets written by the snapshot-copy step that runs once a second input scan has begun — but the value it copies (tracked by the input side across scans) is itself already uninitialized for this component/coefficient combination, tracing back through the same small-object pool to an earlier, unrelated allocation (the color-conversion table built during decompression setup) that never wrote those particular bytes either. So the taint here is not simply "the previous-scan snapshot copy was skipped" (that is the mechanism confirmed for the JNX/28024 sibling instead, whose MSan trace shows no intermediate copy step and traces directly to a different pool reuse) but "the value being snapshotted was itself never initialized by anything upstream." Either way, the block-smoothing routine's precision check then branches on this raw, never-initialized heap value, which MemorySanitizer reports as a use-of-uninitialized-value once the affected scanlines are emitted.
