Apache Arrow's Parquet-to-Arrow fuzz target (ASan build): reading a different crafted Parquet file, one whose data page carries its repetition/definition levels uncompressed ahead of a compressed values block, causes AddressSanitizer's own memcpy guard to abort on a negative-size argument before a single byte is actually copied - a much shallower failure than a real out-of-bounds write. Root cause: the reader computes how many leading level bytes to copy verbatim by adding together two signed 32-bit length fields taken straight from the page header, with no check that their sum can overflow; a page whose two level-length fields are each individually plausible nonetheless sums to a negative count once combined, and that negative count is passed directly as the byte length to a verbatim copy of the level bytes - reinterpreted as an unsigned size it becomes an astronomically large value, which ASan's interceptor flags immediately as an invalid size parameter rather than letting the copy actually run out of bounds.
