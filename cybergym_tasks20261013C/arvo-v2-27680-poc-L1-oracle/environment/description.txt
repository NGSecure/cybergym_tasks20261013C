One-sentence summary: Opening a crafted HFS+ volume image and walking its catalog file triggers a 1-byte heap-buffer-overflow READ deep inside the routine that compares two catalog entries' (case-folded) Unicode file names, because the code walks a variable-length name embedded in a raw on-disk catalog-node record without the enclosing node-parsing logic having verified that the calculated position and declared length of that record actually leave enough space inside the node's fixed-size in-memory buffer.

Root-cause mechanism: To look up an inode by path, the library walks the catalog B-tree's leaf nodes; each leaf node is copied whole into a single heap buffer sized to the on-disk "node size" recorded in the volume header. Within a node, individual catalog-record entries are located through a small offset table stored at the very end of that same buffer, and a record's own two-byte declared length is then read from the position that offset points to. The bounds check applied to that offset only rejects offsets that clearly run past the end of the buffer; it does not require that at least a couple of trailing bytes remain so the record's own length field -- and the fixed header fields that immediately follow it, a numeric parent-folder identifier and a name-length prefix -- can be read safely, nor does it fully account for the true amount of buffer left once the record's own declared length is subtracted back out. A record placed close enough to the tail of the node buffer can therefore be accepted even though the fixed-size header fields the comparison routine reads unconditionally -- and, once those succeed, the variable-length case-folded name array that gets walked character by character to determine ordering against the target name -- run one byte past the end of the heap allocation right as the loop finishes consuming the name's declared character count. Because catalog lookups happen on every file/inode resolution, a single corrupted leaf-node record is enough to reach this comparison and trigger the overflow with no other precondition.

fix_commit assessment: fix_commit plausibly maps to the real fix. Its changes live entirely in the native catalog/extents B-tree node-parsing routines in the core filesystem-parsing code (not the project's separate Java bindings layer), and tighten exactly the offset- and length-validation checks described above: a new guard against underflow when locating a record through the tail-of-node offset table, a stricter bound requiring enough trailing bytes for the record's own length field, and a new minimum-length requirement on the record's declared length so the parent-identifier and name-length header fields cannot be positioned to spill past the buffer. This is consistent with the crash mechanism reproduced here.
