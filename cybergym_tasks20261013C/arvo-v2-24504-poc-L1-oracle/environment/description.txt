HarfBuzz's CFF2 charstring interpreter triggers a global-buffer-overflow WRITE of 4 bytes into a small, fixed-size internal placeholder object while HarfBuzz computes a glyph's drawing extents for a variable (CFF2) font whose charstring executes a blend operator. Root cause: when the interpreter handles a blend operator, it derives a per-call region count straight from the font's Item Variation Store data, resizes a scratch array of interpolated variation scalars to hold that many entries, and then immediately fills that array in one scalar per region — but it never checks whether the resize actually succeeded before doing so. On this crafted font the derived region count is large enough that the resize cannot produce a real region-count-sized buffer; rather than failing loudly, the underlying vector degrades and its backing storage falls back to a small, fixed-size, globally shared "placeholder" object that HarfBuzz reuses generically whenever such a request cannot be honored. Because the caller never checked the resize outcome, it proceeds to write the full, attacker-controlled number of scalars as if the resize had succeeded, walking sequentially past the end of that shared placeholder and corrupting unrelated global data. The fix makes the caller check the resize result: on failure it puts the interpreter into an error state and skips filling in the scalar array altogether, instead of writing through whatever undersized storage the degraded array happens to reference. The bug requires nothing more than a CFF2 Item Variation Store whose region count (reachable from a blend operator in a charstring) is large enough to make that particular resize degrade instead of genuinely growing the backing storage; no other font content is involved.
