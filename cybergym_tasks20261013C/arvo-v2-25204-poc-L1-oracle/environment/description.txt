Alembic's Ogawa-backed archive reader (the alembic_dump_info_fuzzer target; this crash was found by the coverage-guided libFuzzer engine rather than the byte-mutation fuzzer that produced the other two inputs sharing this crash function) hits the same out-of-range metadata-index defect: an index value read straight from the archive's byte stream is used, without validating it against the size of the internal list of already-parsed metadata records, to select a record whose key/value dictionary is then copied into the property header being built. Here the smallest of the three crafted inputs still reliably drives the lookup past the end of that internal list, but the resulting crash happens at a different point in the copy than in the other two: rather than failing while walking pointers between existing tree nodes, this one gets as far as allocating a brand-new node and copy-constructing its key/value pair, and it is the construction of the string value itself that reads a length/pointer header from bytes that were never a real string in the first place, dereferencing a wild, clearly-fabricated address. That makes this the only one of the three where the crash lives one layer deeper, inside the string's own copy machinery rather than inside the tree's pointer-following logic, even though the root defect — the missing check on the archive-supplied index before it is used to index into the metadata list — is identical to the other two.
