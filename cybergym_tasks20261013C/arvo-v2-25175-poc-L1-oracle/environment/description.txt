Alembic's Ogawa-backed archive reader (the alembic_dump_info_fuzzer target) reconstructs property headers by taking an index value directly from the archive's byte stream and using it, without checking it against the size of the internal list of already-parsed metadata records, to select one of those records and copy its key/value dictionary into the header under construction. This much larger crafted input drives the same out-of-range index defect as the smaller inputs that hit the same code path, but the bogus record it produces behaves differently once the copy-assignment begins walking it: the very first element fetch succeeds without tripping any instrumentation, and the walk proceeds to advance across more than one supposed tree node before dereferencing a link that resolves to a completely unmapped page. Rather than the immediate, sanitizer-caught overflow seen on the shorter inputs, this one crashes with a genuine segmentation fault partway through a multi-node copy, because the second stray pointer the traversal follows lies far outside any mapped memory at all rather than just past a heap allocation's boundary. The crash type therefore differs (a hard SEGV instead of an ASan heap-buffer-overflow report) even though the read that eventually triggers it happens inside the same map copy-assignment routine, and the fault ultimately traces back to the identical missing bounds check on the archive-supplied metadata index.
