FFmpeg's format-probing layer (ASan build), while sniffing a raw byte buffer to see if it looks like a 3DO multimedia container, walks a sequence of TLV-style chunks: at each loop iteration it reads a 4-byte tag and a 4-byte declared chunk length from the current cursor, advances the cursor forward by that fixed 8-byte header width, and only then checks the declared length against how many bytes remain in the buffer from the new cursor position. Because the remaining-bytes figure is computed as a plain signed subtraction and then compared directly against the (unsigned) declared length, a chunk positioned so the 8-byte header advance itself already overruns the buffer makes that subtraction go negative; once implicitly reinterpreted as unsigned for the comparison, a negative "remaining bytes" reads as an enormous value that is essentially never smaller than the declared length, so the guard that is supposed to reject an oversized/garbage chunk length never fires. The unrejected, attacker-controlled length is then added onto the cursor to locate the next chunk, which can overflow the loop's own signed cursor variable into a large negative value. The loop's top-of-iteration bound check (cursor less than buffer size) still holds for a negative cursor against a positive buffer size, so the loop does not terminate on a corrupted cursor -- it re-enters and reads the next chunk's tag/length from a wildly out-of-range address relative to the buffer, producing a wild-pointer read/segfault rather than an ordinary small overread near the end of the buffer.
