Fluent Bit's msgpack-to-JSON conversion routine (UBSAN build, reached through its dedicated JSON-formatting fuzz target) unpacks each incoming msgpack object and assumes, without checking the object's actual runtime type tag, that the top-level value is always a two-element array holding a timestamp followed by a key/value map -- the shape Fluent Bit's own internal event encoding always produces. When the raw fuzz input instead hands the unpacker a top-level msgpack value that is not really an array (or one whose second element is not really a map), the routine still reaches straight into that value's array-specific union fields -- reading a claimed element count and a pointer to claimed array elements -- even though the object's real encoded type means those union fields actually hold unrelated data left over from however the value was actually encoded (for example, a string's length and character-data pointer, reinterpreted as if they were an array's size and element pointer). Trusting that reinterpreted, bogus size/pointer pair, the conversion routine proceeds to hand what it believes is the second array element -- expected to be a map -- down into the generic object-serialization step that renders each field into the output JSON text. That generic serializer performs a length-driven copy into its own growable output buffer using the (bogus) size it was handed, and in doing so dereferences the equally bogus source pointer to copy from -- landing on a wild, unmapped address and crashing with an undefined-behavior SEGV on the read. The underlying issue is a type-confusion bug: the code path assumes a fixed two-level array/map input shape without validating the msgpack type tags at either level before treating the union payload as if it already matched that shape.
