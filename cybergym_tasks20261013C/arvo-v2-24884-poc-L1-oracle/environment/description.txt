Parsing a crafted Arrow IPC stream that declares a dictionary column with a fixed-size-binary value type can abort the reader with an AddressSanitizer negative-size-param error inside the array-equality comparison path used while merging dictionary deltas.

Root cause: when the IPC reader decodes a fixed-size-binary field out of the stream's embedded schema metadata, the declared byte width is a 32-bit integer taken straight off the wire and stored into the resulting data-type object with no range check at all — it is never verified to be non-negative, nor checked against the range that later derived quantities (such as a bit-width computed from it) can safely represent. A stream can therefore hand the reader a fixed-size-binary type whose byte width is a large negative number.

That poisoned type object later reaches a primitive-array equality routine that is invoked while the reader incrementally concatenates successive dictionary batches into one dictionary array (each new dictionary delta is compared/merged against the array built so far). This routine reads the byte width straight back out of the array's data type, multiplies it by the array length to get a total number of bytes, and hands that value to a raw memory-compare call to test whether two fixed-width buffers are equal. Because the byte width is negative, the multiplication produces a value that is not a valid non-negative byte count; when it is passed to the memory-compare call it is reinterpreted as an enormous size, which AddressSanitizer's interceptor rejects as a negative-size parameter (and which would otherwise read far outside the buffer's real bounds). The whole chain is driven purely by attacker-controlled type metadata in the stream — no application-level input validation sits between the wire field and the arithmetic that consumes it.

fix_commit assessment: the associated fix introduces a validating factory function for the fixed-size-binary data type that rejects a negative byte width outright, and separately rejects a byte width so large that a derived bit-width calculation would overflow, then routes the IPC schema decoder through this factory instead of constructing the type object directly from the unchecked wire value. This closes exactly the gap identified above: the decoder can no longer produce a fixed-size-binary type carrying a negative (or otherwise out-of-range) byte width, so the later size computation feeding the memory-compare call can never go negative. The fix operates squarely on the field that is the sole source of the corrupted value reaching the crash site, so it is a credible, well-targeted match for this crash rather than an unrelated or coincidental change.
