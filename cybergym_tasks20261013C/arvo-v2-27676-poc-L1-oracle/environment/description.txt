Skia's raster-canvas drawPatch fuzz target (UBSan build): calling SkCanvas::drawPatch with a fuzzer-supplied Coons patch (twelve cubic control points plus four corner colors) causes a segmentation fault. drawPatch tessellates the patch into a triangle mesh and rasterizes it through the software raster pipeline's scanline blitter; the crash happens while that blitter is compositing one destination scanline, at the point where it fetches several packed pixels from the destination bitmap to blend the new color over them. Root cause: the scan-conversion/edge-walking code that rasterizes the tessellated triangles computes, for each scanline it hands to the pipeline, a starting row/column offset into the destination bitmap; because the tessellated geometry is derived from patch control points that are not constrained to sane/finite values, this offset can end up outside -- or, after the pointer arithmetic used to turn it into an address, effectively unrelated to -- the bitmap's real pixel range. Neither the low-level per-pixel address computation used by the pipeline (base pointer plus row-times-stride plus column, with no range check) nor the vectorized pixel-fetch helper's boundary-handling branch (which performs an unconditional partial-width read once it is invoked at a scanline edge) validates the row/column values handed down by the scan converter. So a bad offset produced upstream from the degenerate tessellated geometry is not caught until it is dereferenced as a raw pointer deep inside the pixel-compositing code, producing the observed segmentation fault far from the actual point where the geometry became invalid.
