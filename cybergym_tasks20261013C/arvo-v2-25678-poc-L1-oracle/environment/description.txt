A crafted PHP script triggers a use-of-uninitialized-value read (MemorySanitizer) inside the Zend engine's generator-delegation machinery, because a "yield from" is allowed to register a new delegating generator against a target generator that has already been torn down and still carries a stale reference to a previously freed delegating generator.

Root cause: the engine models chained `yield from` relationships as a small parent/child tree attached to each Generator object, so that resuming a deeply nested delegation chain can walk straight to the innermost active generator. When generator A is first delegated into by generator B (`yield from $A` inside B), the engine records B as A's single child in this tree. The engine also has a distinct notion of a generator being "aborted": once a generator's own execution finishes for any reason other than a normal `return` — in particular, when it throws an exception that propagates out of it uncaught — its underlying execution context is released, but the object itself, and the delegation-tree bookkeeping still attached to it, remain alive as long as something still references it.

Before actually registering a new delegation, the code that implements `yield from` is supposed to reject the target generator outright if it has already been aborted in this way, throwing a catchable engine error instead of touching the delegation tree. The bug is an ordering mistake in that guard: the check that tests "did this generator finish via a normal, capturable return value" is evaluated first, and only the alternate branch of that same check goes on to test whether execution has actually ended. A generator that aborted via an uncaught exception never produced a return value, so it fails the first test and the code falls into the branch that treats it as still live and delegable — the "already aborted, reject" branch is never reached for this case, and the engine proceeds to add the new delegator as a child of the dead generator's tree node.

That tree node, however, can already hold a stale reference: if an earlier delegator that had been registered as this generator's child was itself destroyed in the meantime (its last remaining reference dropped once the exception it received was caught and handled, e.g. by reassigning or discarding the variable holding it), the object it pointed to has already been returned to the allocator and its memory reused/poisoned. Registering the second, new delegation requires walking the existing single-child link to look for further nested children before merging it into a multi-child structure, which dereferences that stale child pointer and reads fields out of memory that is no longer a live PHP object — precisely what MemorySanitizer reports as a read of uninitialized/deallocated storage. The trigger is fully deterministic and needs no external input beyond the script itself: one generator that yields a value and then throws, one wrapper generator that delegates into it and is destroyed after the first thrown exception is caught, and a second, independent wrapper generator that then also delegates into the same now-aborted, now-stale-linked source generator.
