RDKit's binary mol-pickle deserialization fuzz target (AFL driver, ASan build): a wild-address SEGV (read) fires while rebuilding a molecule's ring-membership bookkeeping from a serialized pickle stream, inside the routine that registers a newly-read ring by appending its size into a pair of per-atom / per-bond index-to-ring-size lookup tables. Root cause: the pickle reader that reconstructs each stored ring first reads a ring size and then, per entry, an atom index (and a bond index) straight off the input stream, but -- unlike the analogous mol-file and SMILES/SMARTS text-parsing paths -- performs no bounds or sign checking on these values before handing them to the ring-registration routine: a negative or otherwise out-of-range integer taken directly from the stream is cast to a signed index and used, unvalidated, to index into (and conditionally grow) a per-atom vector-of-vectors. The registration routine's own growth check only resizes the backing structure when an index looks too large, never when it looks negative, so a negative index slips past that guard entirely and the code proceeds to index the backing vector at that position -- which, given how vector indexing resolves a negative offset, lands far outside the actual allocation -- and the fault surfaces the moment it tries to append an entry there. Because the corrupting value comes directly from attacker-controlled pickle bytes rather than from any quirk of a text-format grammar, this is a distinct, unrelated bug from the mol-file bookmark family bundled into the same maintenance commit: it lives entirely in the binary pickle (de)serialization code path, never touching the V2000/V3000 CTAB or SMILES/SMARTS parsers at all.
