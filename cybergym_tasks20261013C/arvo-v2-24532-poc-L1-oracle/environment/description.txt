HarfBuzz's font-subsetting fuzz target (ASan build): a wild-address write occurs while subsetting the CFF outline table of a crafted OpenType/CFF font, in the same general area of the subroutine-subsetting logic as a sibling issue discovered around the same time on a different minimized input, but triggered through a different path and crashing at a different point. As part of deciding which glyphs and subroutines survive subsetting, each surviving glyph's charstring (and each surviving global/local subroutine) is re-interpreted, and every decoded bytecode operator is appended to a growable per-glyph or per-subroutine list; several of these lists are sized once, up front, from counts taken directly out of the attacker-supplied font (glyph count being kept, global subroutine count, local subroutine count per font dict), and that up-front sizing call can silently fail on an extreme count without its caller checking the outcome, leaving the affected list's internal size/allocation bookkeeping inconsistent with what later code assumes it is. Here the crash does not happen while re-visiting an already-recorded entry (no call-into-subroutine bookkeeping is involved); instead it happens the moment the very first ordinary bytecode operator of an already-mis-sized glyph or subroutine entry is appended to its list, i.e. inside the routine that grows the list to make room for the new item. That growth step's bulk zero-fill of the newly claimed slots writes through a size/pointer pairing that was never legitimately established for this particular list, producing an out-of-bounds write and the observed SEGV — no subroutine call needs to occur in the charstring at all for this one to trigger, unlike the sibling issue.
