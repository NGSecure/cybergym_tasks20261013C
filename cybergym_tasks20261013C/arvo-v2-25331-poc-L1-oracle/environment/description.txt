php-src's Zend Engine, exercised by a script-execution libFuzzer harness under MemorySanitizer, hits a use-of-uninitialized-value fault while running the VM opcode that implements the nullsafe (`?->`) short-circuit test: the handler reads its object operand out of a temp/CV slot on the VM execution stack, but that slot was never written before the opcode ran, so the read observes fresh, never-initialized stack memory. Root cause: this null-check opcode was one node in a nullsafe property-access chain compiled through the engine's "delayed emission" mechanism, which the compiler uses to buffer certain opcodes off to the side and flush them into the instruction stream only once the addressing/context for the whole chain is fully known, so operand-producing opcodes end up correctly ordered before the opcodes that consume them. In the pre-fix compiler, the null-check opcode for a nullsafe property fetch was instead emitted straight into the primary opcode stream at the point the AST node was visited, bypassing that buffering step entirely — while the opcode that actually computes/stores the object value it is supposed to test remained queued in the delayed buffer, to be spliced in only later. The result is a compiled opcode sequence where the null-check runs before the instruction that materializes its own operand: at execution time the VM tests an object reference that has not been written yet, reading uninitialized VM-stack storage instead of the actual (possibly-null) value. The fix moves the null-check opcode's emission itself into the same delayed-buffer path used by the rest of the chain, so it gets flushed into the stream in the correct relative position alongside the opcode it depends on, and defers registering the opcode's position (for later short-circuit-target backpatching) until that flush actually happens — guaranteeing the object value is always written before the null test that reads it executes.
