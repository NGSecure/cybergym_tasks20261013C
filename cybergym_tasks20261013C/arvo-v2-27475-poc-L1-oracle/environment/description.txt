Apache Arrow's C++ IPC stream reader also crashes on a different crafted input, this time with a 4-byte out-of-bounds read that lands just past a small library-internal placeholder object the library substitutes for a genuinely empty/unallocated buffer. The overread happens while the reader runs its full structural validator against a single dictionary batch's array data: for a variable-length list-typed column, the validator walks the column's offsets array to confirm that every consecutive pair of offsets describes a valid, non-decreasing slice into the child value buffer, which requires reading one offset entry past the last logical element to compute the final slice boundary. The message in this input declares a list-typed dictionary array whose companion offsets buffer is the library's own empty-buffer placeholder object rather than a real allocation sized to the array's declared element count, so that extra read walks off the end of the placeholder and into unrelated adjacent static data. Unlike the sibling crash that shares this fix, this one is triggered by validating a single dictionary batch in isolation -- no accumulation of multiple delta batches is needed -- and the faulting read sits inside the validator's own bounds-checking logic rather than in any bitmap-merging helper, so the two crashes exercise unrelated code paths that merely happen to both be reachable from the same top-level dictionary-resolution entry point.
