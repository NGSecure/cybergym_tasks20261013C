OpenEXR's scanline reader hits a 1-byte heap-buffer-overflow read while rebuilding the Huffman decode tables used to decompress a PIZ-compressed scanline block from a crafted EXR file. Root cause: the setup routine walks a compact, packed byte array (holding one code length per symbol) field by field, refilling a small bit buffer one byte at a time from that array as each field is decoded; the guard meant to stop this walk once every byte of the array has been consumed treats the read cursor's already-consumed byte count as still within range at the exact value equal to the array's total length, instead of only up to one less than it. A symbol range crafted so the cursor lands precisely on that boundary therefore passes the guard, and the next bit-buffer refill dereferences the very next byte -- one past the end of the heap allocation backing the array -- before the truncation is ever detected. The fix tightens this boundary comparison so a cursor sitting exactly at the array's length is already treated as exhausted (rejected as truncated data) rather than as one more byte still available, and hardens a related length field earlier in the same decompression stage to be validated against the actual remaining input extent -- and rejected outright when negative -- rather than only against a separately-tracked byte count that does not itself catch an out-of-range or malformed value.
