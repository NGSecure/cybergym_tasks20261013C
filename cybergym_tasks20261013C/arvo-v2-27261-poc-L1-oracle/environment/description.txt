Fluent Bit's internal-utilities fuzz target (tests/internal/fuzzers/utils_fuzzer.c) drives a small chained hash-table implementation it links against end to end within a single call: it builds a fresh table whose slot count is taken directly, unvalidated, from one byte of the fuzz input, inserts a batch of records into it, and then loops asking the table to hand back an entry by a purely numeric slot index -- not by key -- where that index is likewise taken directly, unvalidated, from a separate, later byte of the same input with no relationship enforced between the two values. Internally, the table's backing storage is a single heap allocation holding one small fixed-size chain-head record (a hit counter plus an intrusive list head) per slot, sized to exactly however many slots the constructor was asked for -- in this run, a 4560-byte allocation, per the ASan allocation trace running through the table-creation call. The id-based lookup routine's very first action is to index straight into that array using the caller-supplied numeric id, with no comparison of the id against the table's own recorded slot count before doing so. Because the harness derives the table's slot count and the lookup id from two independent, unrelated input bytes, an id that is numerically greater than or equal to the number of slots actually allocated walks the pointer straight past the end of the heap chunk and reads a field of the (non-existent) slot to check whether it holds any entries -- exactly the 4-byte ASan heap-buffer-overflow READ reported, landing 0 bytes past the end of the allocation, i.e. immediately adjacent to the buffer's tail. The corrective change adds a bounds check as the very first thing the lookup routine does: if the requested id is not strictly less than the table's own recorded size, it now returns a "not found" failure code instead of ever dereferencing the out-of-bounds slot.
