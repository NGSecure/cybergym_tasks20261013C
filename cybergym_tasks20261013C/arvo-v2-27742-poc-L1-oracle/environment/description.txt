fluent-bit's msgpack-to-JSON record formatter (used by the JSON/json_lines/stream output paths): a heap-use-after-free read occurs while re-serializing an unpacked record's key/value pairs into the output buffer. Root cause: the formatter walks the input as a sequence of top-level msgpack objects and, for each one, unconditionally treats it as a 2-element array (`[timestamp, record-map]`) and unconditionally treats that array's second element as a map, reading their `via.array`/`via.map` union sub-fields (element/entry pointer and count) without first checking the msgpack type tag of either object. When a crafted input's top-level object is not actually of array type, or its second element is not actually a map, those union sub-fields are read anyway; the bytes obtained this way (belonging to a different union member than the one being interpreted) get treated as a valid entry pointer/count pair for a map that never existed at that address. Because the unpacker's zone allocator recycles/frees the backing storage used for each successive top-level object as unpacking advances, the bogus pointer derived from the wrong-typed union ends up aliasing memory from an already-freed allocation, so iterating and repacking the "entries" through it performs a read on freed heap memory.
