LLVM opt-fuzzer bitcode-parsing target (ASan build): a heap-use-after-free read occurs while materializing a bitcode function whose body invokes a legacy, pre-upgrade form of a masked X86 vector intrinsic. The routine that rewrites such deprecated intrinsic calls into their current form takes the original call instruction's current symbol-table name as a non-owning string view rather than an owned copy, then immediately renames that very instruction (appending a suffix) to free up its old name for the newly created replacement call. Renaming a Value causes LLVM's value-symbol-table bookkeeping to tear down and deallocate the old name's backing storage once the rename completes, so the string view captured a line earlier now dangles into freed heap memory. The routine then reuses that same dangling view to assign a name to the newly created replacement call; assigning a name runs a scan over the requested name's character data (an embedded-terminator sanity check), and that scan dereferences the already-freed bytes, producing the use-after-free read. Root cause: holding a reference-only view into a Value's current name across a statement that renames that same Value, instead of copying the name into independent storage before the rename happens.
