A crafted PHP script triggers a heap-use-after-free read in the Zend engine while it is finishing a nested array/string dimension-assignment expression, because a custom error handler invoked mid-expression is allowed to destroy the very container the assignment is still writing into.

Root cause: the script builds a small associative array and then targets a second-level dimension of one of that array's own elements (which by this point holds a string value) for a further single-character offset write, roughly the shape of `$container[$key][$undefinedIndex] = $x`. To perform this nested write, the engine first resolves the inner array element that will actually be written into, obtaining a direct, mutable pointer straight into that array's own bucket storage rather than a copy — this is needed so the subsequent offset write can inspect and mutate the string in place. Only after that pointer has been captured does the engine evaluate the assignment's dimension operand, which here is a script variable that was never assigned. Evaluating an undefined variable makes the engine emit its "undefined variable" diagnostic, and because the script has installed a user-level error handler via `set_error_handler()`, emitting that diagnostic is not a passive log write: the engine makes a full, reentrant call into the handler's own PHP code right in the middle of finishing the pending write.

The handler reassigns the same outer variable that owns the array (through the superglobal that aliases it), replacing the entire array with an unrelated scalar value. Because nothing else in the running script still holds a reference to that array, this drops its last reference count, and the engine immediately reclaims the array's backing bucket storage as ordinary reference-counted cleanup — including the exact memory the earlier, still-in-progress nested write had already captured a raw pointer into. When the reentrant handler call returns, the interrupted assignment has no way to know its target was invalidated underneath it: it resumes using the same pointer captured before the handler ran and dereferences it to inspect the (supposedly still-live) string value before finishing the offset write, reading through already-freed heap memory.

The bug is script-only and fully deterministic, with no external input needed beyond the PHP source itself: an error handler that overwrites the outer container variable, plus a dimension operand in the nested write that is genuinely undefined at the moment it is evaluated (so the reentrant handler call is guaranteed to fire, and to fire only there — an earlier, unrelated access earlier in the script leaves other loop-relevant variables merely null rather than undefined, so it does not itself trigger the same diagnostic and does not consume the one reentrant opportunity the crash depends on).
