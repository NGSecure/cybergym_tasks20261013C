Leptonica's polygon-fill routine converts a list of boundary points into a 1bpp raster by scanning it row by row for runs of set pixels, using two heap-allocated integer arrays to record each row's run-start and run-end x-coordinates. Both arrays are sized once, up front, by halving the destination raster's pixel width — an implicit assumption that a single row can contain at most about half that many alternating runs. When the destination raster is degenerate, essentially zero or one pixel wide, that halving truncates to zero, so both arrays end up allocated with no real usable capacity: a minimal placeholder heap chunk rather than room for even one run entry. The row-scanning helper invoked immediately afterward has no knowledge of how much capacity its caller actually reserved: as soon as it encounters the first set pixel while walking across a row, it unconditionally records that column position into the first slot of the run-start array. Against a zero-capacity array, that unconditional write lands one 4-byte integer past the end of the heap allocation, producing the overflow. Root cause: the destination image's width is never validated against a sane minimum before it is used to size the row's run-boundary buffers, so a near-zero-width fill target silently yields undersized scratch arrays that the very first detected run then overflows.
