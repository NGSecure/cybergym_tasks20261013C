Apache Arrow's Parquet-to-Arrow fuzz target (ASan build): reading a crafted Parquet file whose compressed data page uses the Brotli codec triggers a genuine global-buffer-overflow write deep inside the third-party Brotli decoder's internal ring-buffer writer, not merely an aborted size check. Root cause: before invoking the codec, the page reader only grows its reusable scratch decompression buffer when the page header's signed uncompressed-size field compares greater than the buffer's current size; a crafted page whose uncompressed-size field is negative fails that comparison against any positive current size, so the scratch buffer is left at whatever small allocation it already held (in this case an essentially empty buffer sitting among other program-wide globals) while that same negative value is then handed to the codec as the destination capacity - once implicitly widened to an unsigned byte count it becomes enormous, so the underlying decoder believes it has virtually unlimited room and happily emits the input's real, undiminished decompressed payload, overrunning the tiny buffer and corrupting unrelated global memory a few bytes past it.
