uWebSockets permessage-deflate fuzzing harness (MemorySanitizer build): a use-of-uninitialized-value warning fires inside the standard library's fixed-size bit-array "set a bit" routine, invoked from a per-chunk lambda that the harness's chunked-delivery helper calls once for every piece it splits the fuzzer-supplied bytes into. Right before that call, the same lambda hands the current chunk to the project's stream-decompression wrapper (the permessage-deflate inflate path), which is expected to hand back either a populated decompressed view or an empty/failed result when the chunk does not decode as valid compressed data for that stream. The lambda does not check which of those two outcomes it got: it unconditionally reads a length off whatever came back and feeds that length straight into the bit-array call, which itself has to inspect the value's bits to decide which underlying word to touch.

On the failure branch, the wrapper's return value is never actually constructed with real contents -- there is nothing to construct, since decompression did not produce anything -- so the storage backing that "no value" state is left exactly as it was on the stack, i.e. uninitialized. Reading a length out of it anyway pulls raw stack bytes rather than a defined size, and that undefined byte pattern is what trips the sanitizer the instant the downstream bit-array routine has to branch on it. This is a decompression-failure/success discrimination gap in the harness's own per-chunk callback, not a property of any specific byte pattern: any fuzzer input that, once split into chunks by the harness's own chunking helper, produces at least one chunk that fails to inflate as valid data for the running stream reaches the same unconditional read-after-failure sequence.

The committed fix edits exactly this callback, adding a check on the decompression call's return value and only performing the length read (and the subsequent bit-array call) when that check indicates a real result was produced -- i.e. skipping the read entirely on the failure branch instead of reading through it. This is a precise, single-purpose guard directly in front of the exact statement the crash trace identifies, not a change anywhere else in the file or in the decompression implementation itself. Looking one commit earlier in this file's history clarifies why the bug existed at all: the immediately preceding change to this same callback had replaced an older two-value return style (which paired the decompressed view with an explicit success flag, so a failed call always yielded a safely default-valued, zero-length pair) with the current single-value optional-style return that the fix now guards -- that earlier change is what introduced the unconditional, unchecked read as a side effect of switching return conventions, without itself adding the corresponding check. The fix under review is exactly that missing check, added back in.

At the content level, fix_commit's causal link to this crash is therefore strong and specific: it touches the same file, the same callback, and the same statement the crash trace names, and the guard it adds is precisely the condition whose absence produces the uninitialized read described above -- not a tangential or unrelated change. One timing wrinkle is worth recording: this id's recorded upstream metadata places the automated verified-fixed build snapshot at a timestamp roughly a quarter hour earlier than fix_commit's own authored/committed timestamp, which on its face is backwards (a build snapshot cannot already contain a commit that had not landed yet). Checked directly against GitHub's commit history for this file rather than taken at face value, that gap is small, isolated to a single automated build-snapshot boundary, and not accompanied by any competing candidate commit that better explains the fix -- the only other commit touching this file in the surrounding window is the earlier regressing change identified above, which moves in the wrong direction (it introduces the bug, it does not fix it). The most plausible explanation is ordinary build/webhook scheduling lag around one automated snapshot rather than a mis-recorded fix_commit, and it is a materially smaller, differently-shaped discrepancy than a prior uWebSockets case reviewed in this batch where the recorded fix touched an unrelated subsystem entirely and the real upstream patch demonstrably postdated the tracked issue's own stop-reproducing point. Here the diff content itself independently corroborates fix_commit against the crash mechanism, so the small timestamp wrinkle is noted but does not undermine treating fix_commit as the genuine fix for this crash.
