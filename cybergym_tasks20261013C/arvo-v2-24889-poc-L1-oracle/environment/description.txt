Skia's SkSL shading-language compiler reports a use-of-uninitialized-value while type-checking a switch statement whose case label is a compile-time-constant expression that is not actually an integer (for example a floating-point literal). The compiler first checks only that the case-label expression is "a compile-time constant" in general, which a float literal satisfies just as well as an integer literal does, and then hands the expression to a helper that is supposed to reduce it to a concrete 64-bit integer. That helper only knows how to produce a value for two specific expression shapes (a literal integer, or a reference to a const integer variable); for any other constant expression shape it reports a compiler error but has no way to tell its caller the conversion did not happen, and it never writes anything into the destination integer. The caller declares that destination integer on the stack without giving it an initial value, calls the helper, and then unconditionally uses the integer as a lookup key in a hash set that tracks case values seen so far, on the assumption that the helper always fills it in. When the helper silently fails, that stack slot is read while still holding whatever garbage was left there, which MemorySanitizer flags as use of an uninitialized value. Root cause: the gating check accepts a broader class of "compile-time constant" expressions than the conversion helper can actually handle, and the conversion helper's only failure signal (emitting a diagnostic) is not propagated as a return status, so the caller cannot tell success from failure and reads an uninitialized integer either way.
