Heap-use-after-free (8-byte read), reported by AddressSanitizer, while an Envoy proxy instance is unwinding a failed startup caused by an invalid bootstrap configuration. Early in initialization, once the cluster manager and runtime subsystem report themselves ready, the server stands up a background health-discovery-service client that opens its own asynchronous gRPC stream on top of the cluster manager's async HTTP client machinery; in this run that stream is torn down again almost immediately (there is no real backing upstream for it to talk to), which frees the small per-stream bookkeeping object right there -- but a stale pointer to it keeps living on inside other server-wide bookkeeping rather than being cleared. A short time later, the bootstrap proves to reference a filter/extension name that does not resolve to anything registered, so the in-progress server construction aborts and deliberately tears itself back down as part of the same startup attempt: thread-local cluster state is unwound, and destroying the per-cluster async HTTP client along the way walks its notion of "still active" streams and issues a reset call through that same stale reference. That reset call reads an 8-byte field out of the small object that had already been released moments earlier during the health-discovery client's own short-lived setup, which is what AddressSanitizer flags as the use-after-free.
