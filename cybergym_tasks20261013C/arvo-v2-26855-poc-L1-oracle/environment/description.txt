libvips (ASan build): the jpegsave_buffer_fuzzer target first hands the raw input bytes to libvips's generic buffer loader, which auto-detects the container format and, for a TIFF-signature input, invokes the TIFF header/directory reader before any save step ever runs. A heavily malformed TIFF whose directory entries are out of order, duplicated, and carry inconsistent field types/counts is not fully rejected during directory parsing. While walking the corrupted directory, the underlying TIFF library sets a color-map field and allocates a small per-channel array sized according to whatever (corrupted) sample-depth value is in effect at that moment. Shortly afterward, while assembling the page/header info from that same directory, libvips's own palette-copying code reads the color map back out of the TIFF handle using a different, larger notion of how many entries the palette should have, so the copy loop walks past the end of the small array that was actually allocated for it. The result is a 2-byte heap-buffer-overflow read one step past the tail of that undersized allocation, occurring purely while the image header is being parsed, before any pixel data has been decoded.
