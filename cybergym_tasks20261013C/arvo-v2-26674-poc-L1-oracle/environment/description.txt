A bug in libass (ASan heap-buffer-overflow, 1-byte write) occurs when parsing an embedded font attachment carried inside an ASS/SSA subtitle script: the font payload is stored as a custom 4-character-to-3-byte text encoding, and before decoding it the output buffer's size is computed from the encoded length using unsigned arithmetic that subtracts one from the length's remainder-by-four. When that remainder is exactly zero (i.e. the encoded payload's length is an exact multiple of four), the subtraction underflows to a huge unsigned value, which then wraps back around when combined with the rest of the size expression, silently under-allocating the buffer by exactly one byte versus what the decode loop actually needs. The decode loop itself is correct and processes every full four-character group the same way, so its very last group writes its third output byte one byte past the end of the now-undersized heap allocation.
