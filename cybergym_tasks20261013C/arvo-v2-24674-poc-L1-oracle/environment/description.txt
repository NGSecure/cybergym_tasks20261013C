A crash in Skia's SkSL shader-language compiler when compiling a shader that accesses a member/field of an enum-typed value, caused by the enum's member-name lookup incorrectly falling through to unrelated identifiers declared in the surrounding scope.

Root cause: when the compiler front-end sees an expression of the form "EnumType.member", it resolves "member" by temporarily switching the active lookup scope to the small scope that was built while the enum's own case list was parsed, then resolving "member" as a plain identifier in that scope. Before the fix, that per-enum scope was constructed as a nested child of whatever scope happened to be active while the enum declaration itself was being parsed, so it kept a live link back up into the enclosing/global scope rather than being a fully self-contained table holding only that enum's own case constants. Because of that lingering link, if the enclosing/global scope also happens to declare some identifier with the same spelling as the requested member — but which is an ordinary variable (a global, a function parameter, etc.) rather than one of the enum's own case constants — the lookup silently succeeds against that unrelated outer-scope variable instead of failing outright. The caller that consumes the lookup result then unconditionally assumes any successfully-resolved identifier must be one of the enum's own case constants, which are always given a stored constant-integer initializer at declaration time, and immediately reads through that stored initializer to build the resulting literal value. An ordinary variable pulled in from the outer scope generally has no such stored initializer (it is null), and the only guard against this assumption was a debug-only assertion that compiles away entirely in release/fuzzing builds, so nothing stops execution from reading through the null pointer, producing the observed SEGV / wild-address read purely from a crafted shader source string fed straight into the compiler (no other input state is involved).

Fix-commit assessment: the linked fix's own commit message describes exactly this class of bug — making each enum's own lookup scope standalone (severing its link to the enclosing scope) precisely so that a later member-name lookup restricted to that scope can only ever resolve a genuine case constant of that enum, and correctly reports "no such field" for anything else, instead of silently mis-resolving to an outer-scope identifier. The same commit also updates the analogous code path used when reconstructing enums from Skia's precompiled/serialized builtin program data, for consistency with the same invariant. This is corroborated by the upstream bug tracker itself: the fix commit was auto-linked by the tracker's own bot as the revision that closes this exact bug report, and the crash occurs inside the very identifier-resolution routine (and its direct caller) that this commit removes/rewrites, in the same source file the crash is reported in. The fix_commit is credible and directly responsible for closing this crash; there is no indication of a mismatch between the reported crash and the linked fix.
