simdjson's DOM parser crashes with a 1-byte stack-buffer-overflow READ (AddressSanitizer) while parsing a JSON document whose top-level value is a number literal made of an extremely long run of digits (far more digits than a normal double needs) followed by more digits/exponent text, so the fast Eisel-Lemire path bails out and the number falls into the slow "big decimal" float-parsing fallback used for numbers that need arbitrary-precision handling to round correctly.

That slow path first copies every digit character of the literal into a fixed-capacity, stack-allocated digit buffer (a small internal struct meant to hold at most a few hundred significant digits) and tracks how many digits it has seen in a separate counter. The digit-copy loop and the digit-count increment are not kept consistent once the input has more digits than the buffer can physically hold: copying into the buffer is correctly guarded so it stops once the buffer is full, but the counter that records "how many digits are logically present" keeps incrementing for every remaining digit character regardless of whether anything was actually written for it. The net effect is that after parsing an oversized literal, the recorded digit count is left larger than the buffer's real capacity, with no later step clamping it back down.

Subsequent stages of the slow float-conversion path (in particular the rounding/normalization step that repeatedly shifts the decimal digits to bring the value into the representable exponent range) trust that counter as the valid extent of the buffer and iterate/index up to it. Because the counter now overstates how much data the buffer actually holds, this step reads one byte past the end of the stack buffer that stores the digits, which is what ASan reports as a 1-byte out-of-bounds stack read.

Root cause, in short: the digit count and the digit buffer's actual filled length can diverge once the input number has more significant digits than the fixed buffer capacity, and nothing re-clamps the count to the buffer size before it is used as a loop/index bound in later rounding logic. Any sufficiently long numeric literal that forces the slow/arbitrary-precision float path (rather than being satisfied by the fast path or by simple truncation) can reach this state.

fix_commit assessment: the fix directly matches this mechanism. It touches the same number-parsing source file responsible for building the decimal representation from the input digits (not a harness/test-only change — a real product-code fix), and its core change is exactly the missing clamp: after the digit-collection loop finishes, it adds a check that forces the recorded digit count back down to the buffer's maximum capacity (and marks the value as truncated) whenever the count exceeds that capacity, closing the gap between "how many digits we say we have" and "how many actually fit." It also loosens the off-by-one bound used while deciding whether to write into the buffer, but the count-vs-capacity divergence is the actual condition the crash relies on, and the fix's added clamp removes exactly that divergence. A new regression test with a very long, malformed-looking numeric literal is added alongside the source fix, consistent with reproducing this exact oversized-digit-run scenario. There is no indication the fix_commit is unrelated or mismatched here.
