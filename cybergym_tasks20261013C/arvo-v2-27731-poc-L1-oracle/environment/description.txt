Apache Arrow's C++ IPC file reader crashes with an out-of-bounds heap read while running its full structural validator over an ordinary record batch, entirely outside any dictionary-related code -- no dictionary encoding, delta batches, or dictionary-resolution step is involved anywhere in reaching this crash. The record batch in question carries a union-typed column, and one of that union's member columns is a variable-length string array whose declared element count is exactly zero. The full validator recurses into every child array to confirm its contents are well-formed, and for a string-typed array that check includes walking the array's offsets buffer to slice out each element's raw bytes and confirm they form valid UTF-8 text. The per-element visiting logic that does this walk never special-cases a length-zero array before it runs: it unconditionally reads the offset entry that would describe where the array's first element begins, even though no such element exists and nothing meaningful was ever written to that position for an empty array. Because this particular string type uses a wide 64-bit offset representation, the resulting read pulls a full 8-byte word from just past the end of whatever small, unrelated buffer happens to sit in that memory position, landing exactly at the boundary of a heap allocation with nothing legitimate behind it. Reaching this path needs nothing more than one ordinary top-level record batch whose schema includes a union with a zero-length string-like member -- the full-validation pass that trips over this walks every array in a batch unconditionally, regardless of whether the batch involves dictionaries at all, which is what separates this crash from the sibling crashes sharing the same fix.
